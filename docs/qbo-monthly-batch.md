The September 29 rollout used a production pilot at the user's request instead of a QBO sandbox. Migration `20260929150000_qbo_bill_batches` passed the isolated database rehearsal and was applied to the application database. After Farmer Boy Ag successfully updated, the user authorized multiple-project runs; production now allows up to 100 explicitly selected projects per run. No live bills, products, budget codes, or source records were changed during development or the controlled rehearsal; deployment itself does not start a run.

Production deployment `6abbcffd5e6bfe0898062737` published the pilot on September 29. `QBO_BILL_BATCH_ENABLED=true` and `QBO_BILL_BATCH_MAX_PROJECTS=1` are set for production. Smoke checks passed for login, all eleven referenced CSS/JS assets, unauthenticated batch rejection (401), and the authenticated idle worker (200, `active:false`). The batch ledger had zero runs before and after the smoke check. A real selected-project financial run remains to be verified before raising the cap. The Windows Netlify post-build static publishing step failed after successful compilation/packaging; deployment used the checked `.netlify/static` output with all referenced assets present, as in earlier releases.

The existing accounting page gains a project selector, **Update selected bills for [month]**, saved progress, project results, issue links and **Retry unresolved projects**. A user click authorizes the selected projects for one company/month. The server requires explicit canonical project IDs; an omitted/empty selection never means all projects. `QBO_BILL_BATCH_MAX_PROJECTS` defaults to 1 (valid range 1–100), enforced for new runs and retries. The worker refreshes catalog, PO details, daily logs and timecards before validating each complete project. Empty months and current bills are skipped. Missing budget codes and products use the existing setup paths. Exact saved customer IDs win; ambiguous customer matches or catalog issues require review. Material/equipment offset confirmation follows the previously approved Direct Costs policy; labor stays on its existing labor account. QBO manual additions, screed prices/classes, numbering and offsets remain owned by the current host service.

The five-minute scheduled resume function only resumes already-authorized runs; it never starts a new monthly run. Closing the browser is harmless. Temporary read failures back off; Procore quota and worker waits retain their stage. Runs older than 24 hours turn remaining projects into actionable issues instead of waiting indefinitely.

Source ingestion uses the configured Billing Procore connection and its company worker lease, isolated from cloning when `PROCORE_BILLING_ENABLED=true`. Ordinary status GETs read PostgreSQL. QBO calls stay in the serialized host relay. Before posting, the worker rebuilds source data and uses the host-reviewed fingerprint. It records durable write intent before the call. If the process dies or loses the response, it re-reads QBO through `prepare`; it does not blindly repeat a bill write. Verified completed saves become successful results; ambiguous results need review. A definitive stale-fingerprint rejection rebuilds review automatically. ## Local validation and later rollout

Use `node --test test/qboBillBatch*.test.mjs test/qboEmptyMonthReview.test.mjs test/qboBillReconciliationRoute.test.mjs test/permissions.test.mjs test/procoreWorkerRouting.test.mjs`, `npx tsc --noEmit`, and focused ESLint. Unit tests use simulated dependencies and do not send financial writes.

Two opt-in rehearsals supplement those tests. `QBO_BATCH_TEST_DATABASE_URL` enables `test/qboBillBatch.integration.test.mjs`; it refuses non-loopback hosts, ports other than 55439, databases without the `qbo_batch_test` prefix, and the configured application DATABASE_URL. It applies the actual batch migration in a fresh test schema, uses real Prisma transactions/constraints, and strictly replaces external API dependencies. `QBO_BATCH_BROWSER_TEST=1` enables `test/qboBillBatch.browser.test.mjs`, which bundles the actual React component into a temporary loopback-only page, mocks every API request and blocks external traffic. It uses installed Edge and the Netlify CLI's esbuild by default; `QBO_BATCH_TEST_ESBUILD` may supply another local esbuild module. See `docs/qbo-monthly-batch-test-results.md` for the September 29 rehearsal.

For an interactive rehearsal, point an isolated environment at a test database and a sandbox QBO host. Apply the additive migration there, generate Prisma, and set `QBO_BILL_BATCH_ENABLED=true` only in that environment. Netlify background and cron routes use the existing server sync secret and fixed application origin. The flag defaults off; it hides the control and prevents worker execution. Do not use the production-connected `npm run build` as a validation command because it applies migrations.

The controlled rehearsal covered mixed successful/blocked projects, worker interruption during posting, duplicate button clicks, quota waits, manual QBO additions, and retry after corrections. Before increasing the production limit, verify a selected project/month through the actual deployed worker and compare its bill, retained manual lines and offsets. No nightly creation schedule is included; it can later call the same run-creation service with a scheduled attribution policy.
